# Attn — review of `main` @ ee4fe41 (#107), 2026-09-02

A whole-codebase sweep: bugs and edge cases, security, refactor and consolidation opportunities, code
to delete, and things to simplify. It is the re-review that [KNOWN-ISSUES.md](KNOWN-ISSUES.md) asked
for ("roughly fifty PRs have merged since [#52] with no comparable re-review"). Like the 2026-08-16
review, this is a frozen snapshot: the defects it records were copied into KNOWN-ISSUES.md in the same
PR, and that file is the one that stays current.

**Method.** Every file under `src/`, `e2e/`, and `scripts/` was read in full, split across six
parallel passes (main-process core; sync/Gmail/DB; outbox/actions/AI; renderer shell and hooks;
composer and mail rendering; tests/scripts/config), followed by cross-cutting scans (duplicate helper
names across files, `knip` unused-export scan, lint suppressions, casts). Every finding below names a
symbol and a `file:line` anchor on ee4fe41 and was verified by reading the surrounding code; the
headline bugs were independently re-verified after the slice passes. Nothing was executed against
Gmail. Anchors drift — read the symbol as the truth.

**Not re-reported.** REF-1, REF-3, REF-4 and GAP-2..7 from KNOWN-ISSUES.md stand as written; where
this review adds new detail to one of them it says so.

---

## 0. The short version

The code is careful and well-commented, invariants are stated at the top of files and mostly held,
and the security posture around untrusted mail bodies is genuinely good: no `dangerouslySetInnerHTML`,
no `allow-scripts`, every render and serialize path gated by DOMPurify, both prior-review security
items (S1, S2) actually fixed. The problems are second-order and fall into four groups:

1. **Decisions made against stale state.** The top bugs share one root cause: a value is captured
   early and never re-validated at the point of write (archive undo built before "already archived"
   is detected; the outbox claim after a long mirror wait; a local Move-to-Inbox that cannot flip
   `is_inbox_visible`).
2. **Copies of a skeleton.** Five sync runners re-implement the same cursor walk; three drain loops
   re-implement the same graceful scheduler; four components copy the mail-frame plumbing; five
   modules parse CSS declarations; the same helper name is defined twice in 22 places.
3. **Compatibility code for a product that has no compatibility contract.** `action_queue` state
   `'failed'` has no writer; `trash`/`untrash` queue kinds are unreachable; the outbox state machine
   is bypassed by raw SQL for most transitions. Several hundred lines can go.
4. **Test seams that leaked into production.** ~42% of the utility runtime is e2e harness code; the
   AI manager carries a fake provider; production keyboard code keys off `data-testid`.

Do first, in this order: B1, B2, B3, B4, S1, then R1 (the generic cursor walk) because it deletes the
most duplicated code, then D1/D2 (legacy compat and unreachable kinds) because they are pure deletion.

## 1. Bugs

Severity is product impact. Confidence is stated where it is not high.

### High

**B1 · `applyThreadDelta` never promotes `is_inbox_visible`, so a local "Move to Inbox" on a
lifetime-hidden thread is invisible.** `src/main/store/mutate.ts:11` `applyThreadDelta` writes
`thread_labels`, `messages.labels_json`, `threads.is_unread/is_starred` and refreshes
`thread_mailboxes`; the only writer of `threads.is_inbox_visible` in the tree is the `persistThread`
upsert (`src/main/sync/persist.ts:155-156`, promote only when `inboxVisibility === 'show'`). The
lifetime sweep stores every thread with `'hide'` (`lifetimeSweep.ts:286`). A user who opens such a
thread from All Mail or search and moves it to Inbox (`actions/index.ts:394`) gets the INBOX label
locally, but every Inbox read requires `t.is_inbox_visible = 1` (ten sites: `queries.ts:424`,
`mailboxMembership.ts:36`, `splits.ts:413`, `notificationQueries.ts:49`, …), so the thread does not
appear in the list, the count, or any split until the poller sees Gmail's `labelsAdded INBOX` and
refetches with `'show'` — at least 15 s online, never offline. Same for undo of an archive on such a
thread and for snooze returns (`scheduler.ts:119/151`). This violates local-first on a user action.
Fix: in `applyThreadDelta`, `UPDATE threads SET is_inbox_visible = 1` when `delta.add` contains
`'INBOX'`; add a `mutate.test.ts` case seeded with `is_inbox_visible = 0`.

**B2 · Archive undo re-adds INBOX to threads that were never in the inbox.** `triage.archive` is
offered in every non-Drafts view and in search (`useInboxCommands.ts:220`), so the target may already
lack INBOX. `actions/index.ts:395` detects this (`archiveWasAlreadyApplied`) and skips the queue row,
but the undo entry was already built at `:285` from `plan.ts:86` `inverseForThread`, which returns an
unconditional `restoreInbox` for `archive` (unlike the trash/spam/move/star branches, which consult
`labels`). `performTriage` reports "Archived" with a live undo; undo applies `add INBOX` locally and
to Gmail. No test covers archive from a non-inbox view. Fix: make the archive/restoreInbox/unsnooze
inverses label-aware (no-op `label` inverse when INBOX was absent), and return "Already there" when
no thread changed.

### Medium

**B3 · Outbox undo window can be bypassed after a long mirror wait.** `outbox/sender.ts:379-406`
`OutboxSender.drain`: `nextDue` selects a queued row with `send_at <= now`, then awaits `beforeRemote`
(the mirror's `waitForIdle`, tens of seconds during an attachment upload). It then evaluates
`planTransition('timer')` against the stale `row.send_at`, and the claim at `:406` is
`WHERE state = 'queued'` with no `send_at` predicate. If the user undid and re-sent during the wait,
the row is queued with a future `send_at` and is sent before the new undo window expires. Fix:
`AND send_at <= ?` on the claim, or reload the row after the wait.

**B4 · One persistently failing thread wedges history polling forever.** `sync/poller.ts:187-213`
`runHistoryCycle` refetches every `refetchThreadIds` entry, tolerates only 404, and advances
`last_history_id` only after the whole loop (`:221`). Any non-404, non-transient error on one thread
(403 on an oversized thread, a persist exception) throws; `schedule()` retries in 15 s
(`:354,365`) and `syncController.ts:517-523` only publishes the failure. Every cycle re-fetches the
whole history window (N threads × 40 quota units) and fails at the same thread, with no checkpoint
progress and no exit. Fix: skip-and-log per-thread failures (or bounded per-thread attempts), advance
the checkpoint, and let the existence sweep repair; at minimum do not re-fetch threads that already
succeeded in the same window.

**B5 · Discarding a draft while its first mirror create is in flight orphans a Gmail draft, which
sync then resurrects.** `outbox/drafts.ts:428-437` `closeDraft` hard-DELETEs an effectively-empty row
with `gmail_draft_id IS NULL`. If `mirror.ts:223` `streamDraftCheckpoint.create` is in flight for that
row (type → 3 s idle → mirror starts → select-all/delete → Esc inside request latency), the create
returns, `UPDATE outbox SET gmail_draft_id` matches zero rows, and the draft stays in Gmail;
`syncRemoteDrafts` imports it as a fresh `drafted` row with the deleted text. Confidence:
medium-high. Fix: when the post-create update reports `changes === 0`, delete the remote draft just
created; or make `closeDraft` transition to `discarding` whenever the mirror is running on the row.

**B6 · A 408 on `sendDraft`/`createDraft` is treated as permanent, contradicting the code's own
comment and its test fixture.** `sender.ts:172` `executeDraftSendProtocol` deliberately lets a create
408 escape as "ambiguous" so it enters Message-ID verification, but `handleError` routes it through
`sender.ts:62` `permanentSendError`, which is true for any 4xx except 404 that is not `retryable` —
and the real client only sets `retryable` for 429/5xx/quota (`gmail/client.ts:126`). The row becomes
`failed`, `reopenPendingOutbox` mints a fresh Message-ID, and a resend can duplicate a message Gmail
accepted. `sender.test.ts:126` passes only because it builds `new GmailApiError(408, …, true)`, a
shape production never produces. Fix: exclude 408 in `permanentSendError` like 404, fix the fixture to
`retryable: false`, assert the row lands in `sending` with verification.

**B7 · A draft the user deleted in Gmail during recovery is reported as sent and never delivered.**
`sender.ts:117-129` `verifyKnownDraft` maps 404 to `'consumed'`; both callers (`:461,497`)
immediately `markSent`. "Consumed" conflates "Gmail sent it" with "deleted from Drafts on another

**B11 · `preserve.ts` strips `background-color` from blocks, silently breaking F6 zero-loss.**
`composer/preserve.ts:121-130,177-186` `materializeInheritedTextStyles` lists `background-color` as

## 2. Security

Nothing here bypasses the AGENTS.md invariants. Verified clean: no `dangerouslySetInnerHTML` or
`allow-scripts` anywhere; all three mail frames use the same scriptless sandbox; every utility handler
narrows its `unknown` input with a guard; spool/attachment paths go through `isPathInside` and
`safeFilename`; dropped files derive paths in the preload via `webUtils.getPathForFile`; OAuth is PKCE
plus state on a loopback listener; tokens sit behind `safeStorage`; remote images are enforced at the
network layer. Prior-review **S1 is fixed** (`OpaqueHtmlNode.tsx:320-329` `sanitizeEncodedHtml` in
both `importJSON` and `importDOM`, pinned by `importSecurity.test.ts`) and **S2 is fixed**
(`mailSanitizer.ts:51-52,62`).

**S1 · Mail links with non-web schemes reach `shell.openExternal` unfiltered — low-medium.**
DOMPurify's default URI regexp admits `tel:`, `sms:`, `callto:`, `xmpp:`, `matrix:`, `cid:`;
`MessageBody.tsx:131` `normalizeMailLink` passes any `scheme:` through; the frames carry
`allow-popups`, so a click lands in `index.ts:377-380` `setWindowOpenHandler`, which calls
`shell.openExternal(url)` for anything. A newsletter can therefore launch arbitrary registered
protocol handlers on click. `mailLinks.ts:37` `linkHref` already restricts to http/https for
linkified text. Fix: allow only `http:`, `https:`, `mailto:` in the window-open handler (main is the
right place — it is the last gate and does not trust the renderer).

**S2 · Mail bodies reach the model with no data/instruction boundary — low-medium.**
`ai/protocol.ts:70-71,96-98` `buildPrompt` inlines `From ${author}:\n${text}` raw, and
`aiContext.ts:12-22` keeps quoted trails so one injected line propagates through every later message.
The system prompt carries the user's own sent-mail style examples, which an injected instruction can
ask the model to echo. Impact is bounded (the user reviews before sending) and model output only ever
enters via `$createTextNode`/`insertText`, never parsed as HTML. Fix: delimit each message and state
that content is data; strip quoted trails with the logic `styleText.ts` already has.

**S3 · Bearer key may be sent over plain HTTP — low.** `shared/ai.ts:146`
`validateAiSettingUpdate('baseUrl')` accepts `http:` for any host. Allow `http:` only for loopback.

**S4 · Residual negative-margin bypass in the quote CSS filter — low.** `mailSanitizer.ts:70`
`NEGATIVE_LENGTH` recognises a minus only after `^`, whitespace, `,` or `(`; `margin-top:
calc(600px*-1)` and `calc(1px/-0.01)` pass (verified). Recipient-side cosmetics only. Fix:
`/(?:^|[\s,(*\/])-\s*\.?\d/`, or reject math functions in margins.

**S5 · Notes.** `ipc.ts:144` `mailRegisterMessageFrame` trusts the renderer's `allowOnce`, and
`remoteImages.ts:54` `MailFrameRegistry` is never cleared on renderer reload/crash — clear it on
`render-process-gone`/`did-start-navigation`. `GmailSignaturePrefixNode.importJSON` (`:24-28`)
sanitizes `style` but `updateFromJSON` copies `textStyle` raw; not exploitable (the outgoing purifier
rewrites every style on serialize), but `LegacyFontNode` sanitizes both. The
`data-attn-remote-src` and `data-attn-opaque` restore-after-sanitize steps (`serialize.ts:77-81,189`)
are the trust boundary and hold because their sources are node-level sanitized; that invariant
deserves a comment at `serialize.ts:74` and a `sanitize.test.ts` case.
